## 개발 목적

TripPilot의 화면을 탭 중심 정보 나열 UI에서 **상황 중심 여행 운영 UI**로 전환한다. 사용자는 휴대폰의 첫 화면에서 스크롤 없이 다음에 처리할 일과 다음 일정을 판단하고, 준비·예약·서류·도구는 필요할 때만 각 전용 화면으로 넓게 열어 본다.

이번 작업의 성공은 색상·일러스트 교체가 아니라 다음 구조를 실제 앱에 정착시키는 것으로 판단한다.

- 출발 전: 가장 중요한 미완료 준비 또는 예약 확인 1건이 첫 화면의 주행동이 된다.
- 여행 중: 가장 가까운 일정이 첫 화면의 주행동이 된다.
- 귀국 후: 사용자가 선택한 귀국 후 정리 항목이 첫 화면의 주행동이 된다.
- `여정 / 준비 / 보관함 / 도움`과 그 하위 탭을 상세 화면에 상시 고정하지 않는다.

## 개발 범위

### 제품·정보 구조

- 여행 목록, 여행 홈, 일정, 준비, 보관함, 도구, Safety Hub의 목적·진입점·Back 동작을 다시 정의한다.
- 여행 상세의 고정 `TripAreaNavigation` 및 `SubPageNavigation`을 제거하고, 여행 홈의 요약 행과 헤더 더보기에서 전용 화면으로 이동하게 한다.
- 여행 상태(출발 전 / 여행 중 / 귀국 후)에 따라 여행 홈의 첫 번째 행동과 보조 요약 순서를 변경한다.
- 예약과 출처를 `보관함` 전용 화면에서 함께 읽되, 기존 예약·출처 데이터와 외부 실행 승인 경계는 보존한다.

### Compose 구현·반응형 레이아웃

- `TripPilotApp.kt`의 루트 조립, destination 상태, 화면 본문을 유지보수 가능한 책임 단위로 나눈다.

- 첫 viewport의 정보 예산을 정의한다. 360dp 폭·기본 글꼴에서 여행 홈은 `여행 맥락 → 다음 행동 → 다음 일정 → 준비 또는 보관함 요약` 순으로 판단 가능한 정보를 우선 노출한다.

## 문서 기반 제약 사항

- 제품의 한 가지 일은 상태에 따라 `다음 준비`, `다음 일정`, `귀국 후 정리`를 빠르게 판단하게 하는 것이다. 정보가 없으면 만들어 내지 않는다.
- 기능 아이콘은 Material Symbols만 사용하고, 이미지 생성 에셋은 장식 목적이라도 이번 화면 재설계의 필수 요소로 포함하지 않는다.
- 앱 shell에서만 system inset을 처리하며 개별 화면이 중복 safe padding을 추가하지 않는다.
- 여행 데이터는 로컬 우선이다. AI 원문·OAuth·권한·외부 실행 경계 및 사용자 확인 흐름을 화면 정리 과정에서 약화하지 않는다.
- 한 화면의 주행동은 하나다. 상태를 색만으로 전달하지 않고 label과 구조로 설명한다.
- 320/360/414/600/840dp 폭 및 font scale 1.0/1.3/2.0에서 날짜·시간·확인번호·주행동을 의미 없는 ellipsis로 숨기지 않는다.

## 목표 화면 구조와 결정 기록

```text
나의 여행
  ├─ 여행 만들기 / 여행 수정
  └─ 선택한 여행 홈
       ├─ 다음 행동 행       → 준비 | 일정 | 보관함
       ├─ 다음 일정 행       → 일정
       ├─ 준비 현황 행       → 준비
       ├─ 예약·서류 현황 행  → 보관함
       └─ 더보기              → AI 초안 | 내보내기·외부 실행 | Safety Hub
```

| 화면 | 첫 화면 책임 | 고정 노출 | 세부 진입 |
|---|---|---|---|
| 나의 여행 | 어떤 여행을 열지 결정 | 여행 상태별 압축 행, 여행 만들기 | 특정 여행 행 |
| 여행 홈 | 지금 처리할 한 가지를 판단 | 여행명·기간·D-day, 주행동, 다음 일정, 요약 행 | 각 요약 행 |
| 일정 | 시간 순서와 당일 일정을 운영 | 얇은 제목줄, 날짜 선택, time rail | 일정 추가/편집, 출처 |
| 준비 | 다음 미완료 체크와 짐을 처리 | 진행 요약 1줄, 그룹형 checklist | 선택 팩·귀국 후 window |
| 보관함 | 예약·서류·근거를 찾고 확인 | 예약/출처를 성격별 문서 행으로 그룹화 | 행 상세/더보기/재확인 |
| 더보기 | 일상적 여행 운영 밖 도구로 이동 | 짧은 도구 목록 | AI 검토, 외부 실행, Safety Hub |
| Safety Hub | 문제 유형과 사용자 메모를 확인 | 비긴급 고지, 문제 유형, 메모 | category, 메모 편집, 승인된 외부 handoff |

### 확정 설계 원칙

1. `개요`는 탭 이름이 아니라 여행 홈이다. 여행 홈은 다른 네 기능을 반복하는 대시보드가 아니라 다음 행동을 결정하는 요약 화면이다.
2. 일자 선택은 일정 화면 안에서만 사용한다. 여행 홈·준비·보관함에는 `DAY 1…N` strip을 상시 표시하지 않는다.
3. `준비`, `일정`, `보관함`은 별도의 전체 콘텐츠 화면이며 Back으로 여행 홈에 복귀한다. 전용 화면 안의 filter는 데이터 필터일 뿐 앱 전역 navigation이 아니다.
4. AI, 외부 실행, 안전은 기능을 숨기는 것이 아니라, 매번 볼 필요 없는 도구를 여행 운영 화면과 분리하는 것이다. 승인 시트와 안전 문구는 그대로 유지한다.
5. 그림·cover는 정보 공간을 점유하지 않는다. 상태 변화가 꼭 필요할 때도 장식은 보조이고 텍스트·행동이 의미의 기준이다.

## 공통 진행 규칙

- 각 Phase는 앞선 Phase의 자체 테스트 완료 후에만 시작한다.
- 구현 중 발생한 이슈는 해당 Phase에서 수정하고 기록한다.
- 체크박스 상태를 실제 진행 상태와 맞게 업데이트한다.
- 문서에 없는 범위 확장은 하지 않는다.
- 요구사항이 불명확하면 가능한 케이스를 나누고 확인 후 진행한다.
- 한 기능은 유지보수 가능한 최소 책임 단위로 나누고, 각 단위의 역할과 경계를 계획에 적는다.
- 계획 밖 옵션/확장/부가 기능을 만들기 위한 분리는 하지 않는다.
- 공통화는 계획 범위 안의 중복을 줄일 때만 수행하고 과도한 추상화는 피한다.
- 기존 프로젝트 API, 공식 SDK, 표준 라이브러리를 우선 검토하고 새 의존성은 범위상 필요할 때만 포함한다.
- 기존 사용자 데이터·사용자 변경·golden은 삭제, reset, 자동 갱신하지 않는다. 실제 기기 또는 emulator visual approval 전 screenshot 변경을 커밋하지 않는다.
- 각 화면 작업을 끝낼 때 `Hallmark · critique`의 Philosophy, Hierarchy, Execution, Specificity, Restraint, Variety 6축을 기록하고 3점 미만 축은 해당 Phase에서 수정한다.

## Phase 1. UX 계약과 화면 맵 재정의

### 목표

구현 전에 화면 책임·전환·viewport 예산을 문서 계약으로 고정한다. 기존 4개 영역 탭과 2개 하위 탭을 단순히 감추지 않고, 기능 parity가 어느 새 전용 화면으로 이동하는지 확정한다.

### 구현 태스크

- [ ] `design/screen-map.md`를 새 트리(`나의 여행 → 여행 홈 → 일정/준비/보관함/더보기`)로 교체하고 compact/600dp 이상 wireframe을 작성한다.
- [ ] 각 화면에 첫 viewport의 필수 정보와 스크롤 뒤에 둘 정보를 구분한다. 여행 홈은 여행 맥락, 주행동, 다음 일정, 보조 요약의 네 블록을 넘지 않게 한다.
- [ ] 상태별 우선순위를 문서화한다: 귀국 후 미완료 window → 여행 중 다음 일정 → 출발 전 미완료 준비 → 첫 일정 기록 → 예약 보관 → AI 초안 검토. 실제 데이터가 없는 상태는 해당 행동을 제안하지 않는다.

### 목표

- [ ] 일정의 날짜 선택은 가로 공간이 부족할 때 overflow/날짜 선택 affordance를 제공하며, DAY button이 타임라인 첫 항목을 화면 밖으로 밀지 않게 한다.

## 잔여 리스크 / 후속 과제

- 실제 여행 중 사용성은 예시 데이터로 완전히 대체할 수 없으므로, 구현 후 사용자에게 360dp 대표 화면과 tablet list-detail 캡처를 먼저 검토받아야 한다.
- destination/state 분리 중 private composable 이동과 기존 testTag 변경이 넓은 UI 회귀를 유발할 수 있다. Phase 1 교체표와 Phase 6 전체 suite를 생략하지 않는다.
- 일부 screenshot golden은 아직 시각 기준의 역사적 결과일 수 있다. 새 IA를 반영하는 golden은 자동 업데이트하지 않고 명시적 승인 후 갱신한다.
- 이 계획은 화면 구조를 다룬다. 이미지 생성 에셋의 허용 슬롯·manifest 정책 변경은 별도 디자인 자산 계획과 사용자 승인 없이는 진행하지 않는다.
