## 최종 목표

TripPilot을 단순 CRUD 화면이 아니라 다음 제품 경험으로 완성한다.

> **출발 전부터 귀국 후까지, 지금 확인할 한 가지를 보여 주는 로컬 우선 여행 브리핑 앱**

기존 `Field Route Journal`의 색상/hero/탭만 남은 부분 적용 상태를 끝내고, 실제 여행 데이터에 연결된 `Trip Briefing` GUI를 구현한다.

- 다음 행동, 여행 단계, 준비 진행, 예약 문서가 한 화면 흐름으로 읽혀야 한다.
- 준비물은 사용자가 전부 직접 입력하지 않아도 되며, 국내/해외 범위에 맞는 구체적인 기본 팩과 항목별 짧은 확인 이유를 제공해야 한다.
- AI는 구조화된 초안만 제안하며, AI/외부 실행은 자동 저장·자동 실행하면 안 된다.
- 모든 여행 데이터는 기존처럼 Room/DataStore 기반의 로컬 우선 구조를 유지한다.

## 시작 전 필수 작업

1. `AGENTS.md`, 구현 계획, 참조 분석, 기존 디자인 문서, 현재 코드/테스트/Room schema를 먼저 모두 읽는다.
2. `git status --short`를 확인한다. 현재 worktree의 변경은 사용자 작업으로 간주한다.
3. 사용자 변경 파일을 삭제, stash, reset, checkout, commit하지 않는다.
4. 병렬개발계획/dev-plan-v2를 사용하지 않는다. 사용자가 명시적으로 병렬개발계획을 요청하지 않은 상태다.
5. 계획을 다시 제안만 하지 말고, **Phase 0부터 실제 문서·코드·테스트를 만든다.**

## 반드시 지킬 범위와 금지 사항

### 절대 금지

- OpenMinis 코드·패키지·Gradle 모듈·DB·OAuth·sandbox·MCP·browser automation 이식
- 자체 백엔드, 계정, 서버 동기화, 결제, 광고, 분석 SDK, 장소 검색, 원격 이미지 CDN 추가
- Grok/Gemini/API key/직접 OpenAI REST/멀티 Provider UI 추가
- Codex token/credential/auth.json/raw CLI command/raw argument를 읽기·저장·로그·backup에 포함
- AI 원문 prompt/response 또는 OAuth 정보를 Room, DataStore, backup, export, logcat에 저장
- 사용자 승인 없는 Calendar write, map/browser open, JSON/ICS import/export, Intent 실행
- destructive Room migration 또는 기존 여행/준비 상태/예약/출처 데이터 유실
- 참조 HTML의 코드·CSS·JS·SVG·문구·사진·지도·관광지·가격·환율·비자·날씨·연락처를 복사 또는 자동 수집
- 도시 사진, 외부 이미지, 무단 에셋 추가. 새 장식이 꼭 필요하면 자체 Compose vector/VectorDrawable만 사용한다.

### 반드시 유지

- local-first 저장, 오프라인 여행 CRUD
- Codex 초안의 명시적 검토/부분 반영
- 링크/지도/Calendar/파일의 별도 사용자 승인 UI
- 기존 기능 parity, 개인정보·외부 전송 경계, 접근성 testTag/semantics
- 기존 backup v1 읽기 및 restore의 “항상 새 TripPilot record 생성” 원칙

## 구현 순서와 Gate

반드시 **Phase 0 → Phase 1 → Phase 2 → Phase 3 → Phase 4 → Phase 5** 순서로 진행한다.

- 다음 Phase는 이전 Phase의 구현·자체 테스트·계획 checkbox 갱신이 모두 끝난 뒤에만 시작한다.
- Gate 실패 시 원인을 고치고 재검증한다. 외부 계정/장비 의존으로 막히면 근거를 남기고 사용자에게 필요한 단 한 가지 조작만 요청한다.
- 각 Phase 끝에 구현 계획의 해당 checkbox를 실제 통과 항목만 `[x]`로 바꾼다.
- 매 Phase마다 변경 파일, 실행 명령, PASS/FAIL, 보안·승인 경계, 미해결 이슈를 `docs/test-matrix.md`에 누적한다.

## Phase 0 — 디자인 기준과 정보 구조 확정

### 구현

- `design/design-direction.md`를 `Trip Briefing` 기준으로 갱신한다.
- 기존 Field Route 요소 중 유지할 것(색의 의미, 날짜 흐름)과 교체할 것(장식성 ribbon, hero 중심 카드)을 명확히 적는다.
- `design/screen-map.md`에 compact/medium/expanded 화면 맵과 wireframe을 실제 구현 대상 기준으로 갱신한다.
- `JourneyStageStrip`, `BriefingPanel`, `DocumentRow`, `ChecklistGroup`, `TimelineEntry`, `ApprovalSheet`의 input/state/accessibility/testTag 계약을 작성한다.
- 목록·브리핑·일정·준비·보관함·도움에서 한 화면의 primary action이 하나가 되도록 정보 계층을 확정한다.
- 기존 hero asset은 목록 표지에만 유지할지, vector 기반 travel cover로 대체할지 visual audit 근거와 함께 결정한다. 랜덤 사진/배경을 추가하지 않는다.

### Gate / 테스트

```bash
python3 scripts/verify_phase0_design.py
git diff --check
```

- 문서의 용어, screen map, component contract, token이 일치해야 한다.
- 현 상태 screenshot과 개선 후 비교 대상 화면을 고정한다.

## Phase 1 — Trip Briefing shell과 공통 GUI

### 구현

- `TripBriefScaffold`를 도입하여 compact sticky title, safe inset, snackbar, adaptive pane을 통합한다.
- 큰 `TripDetailHeader`를 브리핑 전용 travel cover와 다른 탭의 compact header로 분리한다.
- 기존 `RouteRibbon`의 고정 인자 사용을 없애고, 실제 여행 날짜·선택 일자·준비/초안/승인 상태를 받는 `JourneyStageStrip`으로 대체한다.
- 데이터가 없으면 완료/진행 상태를 꾸며 내지 말고 “일정 없음”을 명확히 표현한다.
- 반복 `Card` stack을 없애고 briefing panel, group section, document row, timeline row의 역할 있는 surface로 통일한다.
- `TripAreaNavigation`과 sub-navigation의 선택·비선택·disabled·TalkBack semantics를 정리한다.
- 목록의 빈/한 개/여러 개 여행을 동일한 Trip Briefing entry 구조로 정리한다.

### Gate / 테스트

- stage calculation unit test: 1일/다일/시작 전/여행 중/종료 후/일정 없음
- list/detail local-only navigation instrumented test
- light/dark, 360dp/600dp/840dp screenshot smoke
- static search로 고정 `completedDays=0`, `selectedDay=1` 호출이 남지 않는지 확인

## Phase 2 — 브리핑·일정·여행 서류 GUI

### 구현

- `브리핑` 화면에 다음 준비 행동, 여행 단계 요약, 미완료 준비 그룹, 다음 예약, 출처 확인 상태를 우선순위로 배치한다.
- `일정`은 날짜 selector와 time rail로 구성한다. 실제 itinerary의 all-day/시각/장소/notes/출처 상태를 표현한다.
- 일정 입력/수정 bottom sheet에서 개인 메모를 기록할 수 있게 하고, 팁·주의는 사용자가 직접 입력하거나 검토 승인된 AI draft에서만 반영한다.
- `보관함` 예약을 예약처/상태/확인번호/시간/장소/연결 출처가 읽히는 document row로 구현한다.
- 출처의 마지막 재확인, pending reservation share, 빈/오류/긴 텍스트 overflow UI를 개선한다.
- link text 표시만으로 Intent를 실행하지 않는다. 실제 열기는 기존 명시적 확인 UI를 통해서만 가능해야 한다.

### Gate / 테스트

- itinerary grouping/sort/all-day/long notes/location unit + instrumented test
- reservation/source CRUD, source owner cascade regression
- 0/1/N itinerary·reservation·source screenshot audit
- 사용자 확인 전 browser/map Intent 호출 0건 regression

## Phase 3 — 세분화된 준비물 팩, migration, backup

### 구현

- 최소 책임 모델을 만든다.
  - `ChecklistTemplateId`
  - `ChecklistGroup`
  - `ReadinessTemplateCatalog`
- 기본 준비물은 다음 그룹을 사용한다.
  - 서류·입국
  - 결제·현금
  - 통신·전자기기
  - 의류·현장 용품
  - 건강·위생
- 각 기본 항목은 제목만이 아니라 짧은 `why/check` 안내를 제공한다.
- 특정 국가의 비자 기간, 전압, 날씨, 환율, 긴급전화, 병원, 의료·법률 지시는 기본 템플릿에 넣지 않는다. 국가별 확인은 “공식 출처에서 직접 확인” 항목과 사용자가 연결한 출처로만 표현한다.
- `AUTO`/`DOMESTIC`/`INTERNATIONAL` 기본 팩을 재구성하고, 국제 기본 팩은 필수와 선택 항목을 구분한다.
- `PreparationItemEntity`, `PackingItemEntity`에 nullable `templateId`를 추가한다.
- Room `v1 → v2` migration을 작성한다. destructive migration은 절대 사용하지 않는다.
- 기존 DEFAULT item은 origin/title matching으로 display metadata를 역추론하되, MANUAL/AI/DONE/SKIPPED/quantity/checked 값은 변경하지 않는다.
- repository default-add와 scope 변경은 template idempotency를 보장해야 한다. 같은 팩을 두 번 적용해도 중복 항목이 생기지 않아야 한다.
- backup v2에서 templateId를 보존하고, backup v1 decode/restore는 계속 지원한다. restore는 기존 trip을 덮어쓰지 않는다.
- 준비 화면은 group·hint·progress·선택 팩·직접 추가로 구성한다. 수동/AI item은 안전하게 `직접 추가` 그룹으로 보인다.
- 귀국 후 팩은 자동 추가하지 않는다. 사용자가 명시적으로 선택할 수 있는 local optional pack으로만 제공한다.

### Gate / 테스트

- catalog unit test: scope별 항목/중복 없음/지역 사실 없음
- repository test: 최초 생성, 재적용, scope 변경, MANUAL/AI/DONE/SKIPPED 보존
- v1→v2 migration test: title/status/origin/quantity/checked 보존
- physical Samsung에 이미 존재하는 local trip의 migration 보존 확인
- backup v1 decode, v2 round-trip, invalid templateId/unknown input safe handling test
- TalkBack label에 그룹·확인 이유·완료 상태가 포함되는 instrumented test

## Phase 4 — 입력·AI 초안·외부 승인 GUI 정합성

### 구현

- 여행, 일정, 준비, 짐, 예약, 출처 입력을 keyboard-safe modal bottom sheet로 통일한다.
- keyboard/IME/back/dismiss/validation/error/process recreation을 구현하고 testTag migration은 테스트와 함께 수행한다.
- AI는 `제안 → 항목별 검토 → 선택 반영`만 제공한다. prompt/response 원문과 credential은 저장하지 않는다.
- Calendar, map/browser, 파일, OAuth는 기존 승인 흐름을 보존하고, 사용자 확인 전 어떠한 외부 실행도 하지 않는다.
- 긴급대처 UX는 사용자가 작성한 안전 메모/출처 진입 구조에만 반영한다. live 정보, 국가별 전화, 의료/법률 지식 자동 제공 기능을 만들지 않는다.

### Gate / 테스트

- keyboard/IME/back/rotation/process recreation/invalid form instrumented test
- AI 계약 위반/stream stop/OAuth unavailable에서 DB/Calendar/Intent/file 작업 0건
- Calendar/map/browser/SAF가 approval dialog 전 실행되지 않음
- draft review/external confirmation/bottom sheet screenshot audit

- screenshot goldens/contact sheet를 새 UI 기준선으로 갱신하고, 바뀐 이유를 기록한다.

- 360dp/600dp/840dp 상태에서 같은 정보 우선순위가 유지되는지 확인한다.

## 실제 사용자 승인 필요 시

- OAuth 로그인, browser authentication, release signing, connected Samsung 권한 등 사용자 계정/자격증명/실기기 확인이 필요한 경우 credential을 요구·저장·출력하지 않는다.
- 자동 테스트와 구현을 끝낸 뒤, 필요한 사용자 조작을 하나씩 명확히 보고하고 대기한다.
