# implement_20260817_230622.md

작성 일시: `2026-08-17 23:06:22 KST`

이 문서는 참조 여행 플래너에서 분석했지만 TripPilot에 일부만 반영된 **문제 발생 시 대응, 한국 복귀 후 할 일, 준비물 전체 구조**를 실제 앱 기능으로 완성하기 위한 순차 개발 계획이다.

## 개발 목적

TripPilot 사용자가 출발 전 준비뿐 아니라 여행 중 문제가 생겼을 때 자신이 저장한 정보와 일반형 대응 순서를 오프라인에서 확인하고, 귀국 후에는 시점별 정리 항목을 선택적으로 관리할 수 있게 한다.

현재 상태는 다음과 같다.

| 영역 | 현재 구현 | 이번 목표 |
|---|---|---|
| 준비물 | 29개 stable template ID, 5개 그룹, 국내/해외 필수·선택 팩 | 참조 항목과 현행 카탈로그의 gap을 전수 판정하고 누락된 일반형 항목 보강 |
| 문제 대응 | 분석 문서와 일부 예방 준비물만 존재 | 7개 일반형 대응 카테고리, 로컬 안전 메모·사용자 연락 정보·출처 연결 구현 |
| 귀국 후 | 영수증 정리·반납 확인 2개 선택 항목 | 귀국 후 48시간/1주/나중의 시점별 선택 팩과 사용자 추가 항목 구현 |
| 여행 단계 | `귀국 후` stage label만 존재 | 실제 날짜와 선택한 귀국 후 항목 상태에 근거한 stage summary/CTA 구현 |

이 기능은 긴급 서비스, 의료·법률 자문, 국가별 최신 정보 제공자가 아니다. 변동 가능한 사실은 사용자가 공식 출처를 직접 확인하고 로컬에 저장하게 한다.

## 설계 결정

### 1. 문제 대응은 정적 일반 가이드 + 사용자 소유 정보로 분리

정적 `ProblemResponseCatalog`은 다음 7개 카테고리만 제공한다.

1. 여권·신분·여행 서류
2. 질병·부상
3. 도난·분실
4. 카드·현금·결제
5. 교통·예약·항공 지연
6. 휴대폰·통신
7. 기상·현장 상황

각 카테고리는 `즉시 안전 확보 → 사용자가 저장한 연락처/공식 출처 확인 → 필요한 기록 보존 → 후속 확인` 수준의 일반 순서만 제공한다. 구체적인 번호, 기관, 치료, 신고 의무, 보상 가능 여부를 단정하지 않는다.

사용자 데이터는 별도 `SafetyMemoEntity`에 저장하고 정적 문구와 혼합하지 않는다. 연락값은 앱이 자동 실행하지 않고 복사 또는 명시적 ApprovalSheet 이후 handoff만 허용한다.

### 2. Help의 두 하위 탭 계약 유지

현재 `AI 초안/외부 실행` 두 탭은 유지한다. Help 상단에 `문제 발생 시·안전 메모` 진입 panel을 두고, 선택하면 Help 내부의 별도 Safety Hub 화면으로 전환한다. Safety Hub는 세 번째 tab이 아니며 Back으로 기존 Help 화면에 복귀한다.

Safety Hub 표시 순서:

1. “긴급 서비스가 아님”과 공식 정보 재확인 안내
2. 7개 문제 대응 카테고리
3. 사용자가 저장한 연락 정보·개인 메모
4. 사용자가 직접 연결한 출처
5. 추가/수정/삭제 및 승인된 외부 열기

### 3. 귀국 후 시점은 템플릿 메타데이터와 준비 항목에 보존

`PostTripWindow`를 다음 세 값으로 정의한다.

- `WITHIN_48_HOURS`: 귀가 확인, 분실·파손 확인, 대여품/통신 임시 서비스, 즉시 필요한 영수증·기록
- `WITHIN_ONE_WEEK`: 비용·영수증 정리, 보상/보험 신청 필요 여부 공식 확인, 사진·데이터 백업, 장비 정리
- `LATER`: 문서 보관, 불필요한 공유·예약 정보 정리, 여행 메모·다음 여행 참고

자동으로 항목을 생성하지 않는다. 사용자가 `귀국 후 팩 추가`를 누른 뒤에만 진행률에 포함한다. 직접 추가한 귀국 후 항목도 window를 선택할 수 있게 한다.

### 4. 데이터·호환 계약

- `PreparationItemEntity`에 nullable `postTripWindow`를 추가한다. null은 기존 출발 전/일반 항목을 의미한다.
- `SafetyMemoEntity`를 trip cascade 소유 테이블로 추가한다.
- 안전 메모 출처는 기존 `SourceEvidenceEntity`와 `SourceOwnerType.SAFETY_MEMO`를 재사용한다.
- Room `MIGRATION_2_3`은 기존 행을 변경하지 않고 새 nullable column/table/index만 추가한다.
- Backup v3는 post-trip window와 safety memo를 포함한다. v1/v2 decode는 유지하고 restore는 새 여행 레코드로 복사한다.
- 사용자 연락·메모는 debug log, analytics, AI prompt, notification 본문에 포함하지 않는다.

## 공통 진행 규칙

- Phase는 `1 → 2 → 3 → 4 → 5` 순서로 진행하고, 이전 Phase 자체 테스트가 통과하기 전 다음 Phase를 시작하지 않는다.
- 정적 일반 가이드와 사용자가 저장한 사실을 UI·데이터에서 명확히 구분한다.
- 변동 가능한 정보는 “공식 출처에서 직접 확인”으로 표현하고 앱이 최신 상태를 보장하는 것처럼 쓰지 않는다.
- 모든 안전 메모와 귀국 후 항목은 local-first이며 AI prompt로 보내지 않는다.
- 외부 URL·전화·지도 동작은 기존 ApprovalSheet 경계를 재사용한다.
- Room schema 변경 전 migration/backup 테스트를 먼저 작성하고 fallbackToDestructiveMigration을 금지한다.
- 기존 manual/AI/DONE/SKIPPED 준비 항목을 migration이나 팩 추가가 변경·삭제하지 않는다.
- optional pack 추가는 stable template ID 기준으로 idempotent해야 한다.
- 사용자 소유 실기기에는 instrumentation/uninstall/clear를 실행하지 않는다.
- 현재 사용자 변경을 stash/reset/delete하거나 계획 밖 commit에 포함하지 않는다.
- material impact·재발 위험·QA escape·보안/개인정보/무결성 near-miss만 occurrence 후보로 기록한다.
- 구현 종료 전 occurrence 후보를 `plan-only | existing-reference | new-lesson`으로 분류한다.

## 잔여 리스크 / 후속 과제

- 정적 일반 가이드는 최신 기관 정보가 아니므로 사용자가 저장한 공식 출처의 재확인 시각을 함께 보여 줘야 한다.
- 실제 TalkBack 음성 흐름과 긴급 상황에서의 인지성은 자동 semantics test 외에 수동 접근성 검수가 필요하다.
- 전화번호 복사 이후의 실제 통화 결과, 외부 앱 가용성, 국가별 긴급 서비스는 앱이 보장하지 않는다.
- post-trip 알림은 기존 reminder 계약과 별도 사용자 opt-in 설계가 필요하므로 이번 범위에서는 화면 내 CTA까지만 구현한다.
