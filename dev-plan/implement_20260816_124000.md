## 개발 목적

OpenMinis와 코드·빌드·데이터 의존성이 없는 신규 Android 앱 **TripPilot**을 Kotlin·Jetpack Compose로 만든다. 여행 관리의 기본 기능은 로컬에서 독립적으로 동작하게 하고, AI 계획 기능은 `alpine-codex-cli-client`가 제공하는 **CLI 소유 Codex OAuth/런타임**을 제한된 어댑터로만 연결한다.

Codex는 구조화된 여행 **초안**만 반환한다. TripPilot DB 변경, 캘린더 추가, 지도·예약 페이지 실행은 언제나 TripPilot의 검증과 사용자의 명시적 승인 뒤에만 수행한다.

## 문서 기반 제약 사항

- TripPilot은 OpenMinis를 **기능 요구사항 참고 자료**로만 사용한다. 새 프로젝트의 소스·빌드·실행 결과물에는 OpenMinis 모듈을 포함하지 않는다.
- Codex OAuth와 자격 증명 수명주기는 공식 Codex CLI가 소유한다. TripPilot은 CLI token, credential 파일, `auth.json`을 읽거나 복사하거나 백업하지 않는다.
- `alpine-codex-cli-client`는 단순 OAuth SDK가 아니라 Alpine/PRoot·Python Gateway·Codex CLI 런타임을 포함한 프로젝트다. 외부 프로젝트의 전체 `:app` 또는 Grok 기능을 의존성으로 포함하지 않는다.
- v1의 Codex 런타임은 외부 프로젝트의 현재 제약을 따라 `minSdk 26`, `arm64-v8a`를 기본 지원 조건으로 검증한다. 지원 ABI 확대는 이번 범위에 포함하지 않는다.
- AI 미연결, 네트워크 없음, OAuth 취소 상태에서도 로컬 여행 데이터 기능은 계속 사용 가능해야 한다.
- Codex가 제안한 결과는 유효한 `TripPlanDraft` 계약을 통과한 뒤에도 자동 반영하지 않는다.
- `alpine-codex-cli-client` 및 그 포함 구성요소의 GPL·상위 라이선스·CLI 배포 조건은 배포 전에 별도 검토한다. 이 계획은 법률 자문을 대체하지 않는다.
- visual direction은 `MaterialTheme`의 color·typography·shape 토큰 위에 구현한다. 기본 Material 화면을 그대로 조합하지 않으며, 브랜드 색의 의미가 깨지므로 v1에서는 동적 색상을 기본값으로 사용하지 않는다.
- 제품 내 필수 시각 에셋은 자체 제작 벡터와 Material Symbols로 제한한다. 네트워크 사진·지도 이미지는 v1의 제품 의존성이 아니다.
- 여행 백업은 Android Storage Access Framework로 사용자가 고른 단일 파일만 읽고, 새 Trip 사본으로만 복원한다. OAuth, 대화, browser cookie, Calendar ID, 대기 외부 작업은 백업·복원하지 않는다.
- 공유받는 예약 입력은 `text/plain` 텍스트/URL만 허용하고, 사용자가 대상 여행과 저장 여부를 고른 뒤에만 짧은 수명의 로컬 intake로 유지한다. 파일·이미지·전체 share MIME은 받지 않는다.
- 기존 OpenMinis 날씨 기능은 `android-weather` 도구에 의존한다. 신규 TripPilot은 전용 날씨 API를 추가하지 않으며, Codex runtime이 승인된 research 응답을 제공할 수 있을 때만 **정보성 Weather Advisory 초안**을 보여준다. 일정·예약·체크리스트를 자동 변경하지 않는다.

| 예약 AI 초안 | URL/원문을 Agent가 분석해 JSON을 만들고 사용자가 필드 검토 후 저장 | **적용**: `ReservationDraft` 계약, 수동 붙여넣기와 Codex stream 양쪽을 검증·승인 경로로 통합 | 3, 4 |
| 여행 AI 계획 | 일정·예약·출처·준비/짐 제안·warning을 구조화하고, 선택 항목만 반영 | **적용**: `TripPlanDraft` 계약, 일정 충돌 warning, REVIEW_REQUIRED, 항목별 수정·제외·transaction 반영 | 3, 4 |
| 기존 Chat 초안 불러오기 | OpenMinis에 저장된 과거 chat text에서 동일 여행 JSON을 탐색 | **의도적 미적용**: 새 앱은 범용 chat을 보관하지 않는다. 대신 검증된 JSON 수동 붙여넣기와 현재 Codex 세션 결과만 검토한다 | 3 |
| 날씨 참고 | OpenMinis `android-weather` tool을 사용해 Agent 대화를 열고 일정은 변경하지 않음 | **조건부 변형 적용**: runtime이 승인된 research 결과를 제공할 때만 `WeatherAdvisoryDraft`를 표시한다. 전용 날씨 API/키는 추가하지 않으며, unavailable이면 기능을 숨기거나 미지원 상태를 표시 | 4 |
| Calendar 승인 ledger | 일정별 선택·승인·제외·실패·재시도, event marker로 중복 생성 방지 | **적용**: TripPilot 전용 action ledger, 선택 항목만 Calendar Provider write, 부분 실패는 실패 항목만 재시도 | 5 |

| 여행 JSON 백업·복원 | 제한된 크기의 versioned JSON, 새 ID로 독립 사본 복원, 토큰·chat·cookie·Calendar ID 제외 | **적용**: 사용자 선택 파일만 허용하고 legacy `openminis.trip-backup` v1은 reader 호환, 새 export는 `trippilot.trip-backup` v1로 고정 | 2, 5 |
| 기본 Agent 바로가기 | OpenMinis 범용 ChatScreen으로 이동 | **대체 적용**: TripPilot 내부의 제한된 `AI 초안 만들기`/`Codex 연결` 화면. 범용 terminal/chat/skill UI는 만들지 않음 | 3, 4 |
| 미사용 Place 데이터 테이블 | 기존 entity는 존재하지만 TripPilot UI·repository 사용자 흐름에 연결되지 않음 | **미적용**: 별도 Place DB는 만들지 않고 일정/예약의 `location` 값으로 유지 | 제외 |
| 일반 PendingAction 확장성 | 실제 사용자 흐름은 Calendar action ledger에 한정 | **변형 적용**: generic JSON action queue는 만들지 않고 CalendarAction 전용 상태 모델로 제한 | 5 |

### 분석 결과와 보완 조치

기존 계획에서 빠져 있던 **여행 범위별 기본 템플릿, Preparation/Packing 이원화, opt-in readiness reminder, 예약 URL/text share intake, 수동 JSON 붙여넣기, JSON 백업/복원, ICS, Calendar ledger 재시도**를 아래 Phase 태스크와 테스트에 추가한다.

새 제품 목적과 충돌해 이식하지 않는 범위도 명시했다. OpenMinis의 일반 chat history, browser automation, `android-weather` device tool, 전체 MIME 첨부 share, raw agent command, Place table은 독립 TripPilot의 필수 기능이 아니며 새 구현에 포함하지 않는다.

## 전문가 재검토 및 확정 제안 (2026-08-16)

### 검토 결론

기존 계획의 제품·보안 경계는 적절하지만, **디자인 단일 출처, 에셋 출처 정책, 시각 회귀 검증, 초기 Gradle 복잡도 제어**가 빠져 있었다. 이를 고정하지 않으면 기능은 완성돼도 화면마다 표현이 달라지고, 외부 이미지를 뒤늦게 넣으면서 라이선스·네트워크·APK 용량 문제가 생길 수 있다.

따라서 구현 시작 전 `Phase 0`에서 시각 언어와 에셋을 확정하고, 이후에는 그 결정만 사용한다. Compose Material 3는 색상·타이포그래피·shape를 하나의 theme로 적용할 수 있으므로, TripPilot은 이를 기반으로 하되 여행 도메인에 맞는 자체 경로 UI를 만든다. [Material 3 in Compose](https://developer.android.com/develop/ui/compose/designsystems/material3)

### 디자인 방향: Wayfinding Field Journal

- **사용자와 한 가지 일:** 출발 전에는 무엇을 준비해야 하는지, 여행 중에는 지금 어디로 가야 하는지를 가장 빠르게 확인하게 한다.
- **시각 은유:** 지도 카드나 관광 사진이 아니라, 실제 여행의 `동선·날짜·확인 상태`를 표현하는 **Route Ribbon(경로 리본)** 을 제품의 단일 시그니처로 사용한다.
- **구성:** 여행 상세 상단의 기간 축에서 리본이 이어지고, 일자·일정·준비물 완료·예약 확인·AI 초안은 그 경로의 서로 다른 상태로 표현한다. 장식용 선이 아니라 시간 순서와 승인 상태를 읽는 정보 구조다.
- **절제:** 리본 이외에는 평면 surface, 충분한 여백, 명확한 label과 상태 chip을 사용한다. 무의미한 glassmorphism, 도시 사진 배경, 과도한 gradient, 장식용 애니메이션은 사용하지 않는다.

- **Edge-to-edge:** target SDK 35 이상에서는 edge-to-edge가 강제될 수 있으므로 status/navigation bar inset을 디자인·테스트 대상에 포함한다. [Android edge-to-edge guidance](https://developer.android.com/develop/ui/compose/system/setup-e2e)

### 한 번에 개발 완료하기 위한 보완 원칙

1. **프로젝트 구조를 먼저 작게 고정한다.** 초기에는 `:app` 한 모듈과 package boundary로 구현하고, Codex adapter의 독립성이 검증될 때만 분리한다.
2. **외부 이미지를 제품 의존성으로 만들지 않는다.** 지도·도시 사진·무료 이미지 API는 API key, 네트워크 실패, 라이선스, 캐시 정책을 새로 만든다. v1의 목적과 무관하므로 제외한다.
3. **테스트 가능한 디자인을 만든다.** UI label/testTag, light/dark, font scale, screenshot golden을 처음부터 component contract에 넣는다. Compose의 semantics·text scaling·accessibility checks가 이를 지원한다. [Compose accessibility](https://developer.android.com/develop/ui/compose/accessibility)
4. **성능은 출시 직전에 덧붙이지 않는다.** 앱 시작, 여행 목록, 상세, AI 검토 흐름을 Baseline Profile 대상으로 정하고 final release에서 측정한다. Baseline Profile은 첫 실행과 공통 상호작용의 실행 성능을 개선하도록 설계돼 있다. [Android Baseline Profiles](https://developer.android.com/topic/performance/baselineprofiles/overview)
5. **Codex risk는 UI 완성 전후로 격리한다.** Phase 3까지 fake runtime으로 제품 흐름을 끝내고, Phase 4에서만 CLI runtime을 교체한다. Alpine 통합이 변경돼도 여행앱의 도메인·디자인·QA는 재작업하지 않는다.

- 각 Phase는 앞선 Phase의 자체 테스트와 완료 조건이 모두 충족된 뒤에만 시작한다.

- 한 기능은 유지보수 가능한 최소 책임 단위로 나누며, 계획 밖 옵션·확장·부가 기능을 위한 추상화는 만들지 않는다.
- 기존 Android API, 공식 SDK, 표준 라이브러리를 우선 사용한다. 새 의존성은 기능·보안·재현성 필요성이 확인된 경우에만 추가한다.

- 모든 포함 에셋은 `docs/asset-manifest.md`에 파일명, 용도, 출처/생성 방식, 라이선스, 변형 여부, hash를 기록한다. 외부 원격 이미지 URL을 런타임에 호출하지 않는다.

- 개발 종료 전 후보를 `plan-only | existing-reference | new-lesson`으로 분류하고, 재사용 가능성이 확정된 경우에만 Dev Lesson으로 승격한다.

## Phase 4. Alpine Codex OAuth 연동

### 목표

Phase 1에서 검증한 최소 통합 경계를 통해 Codex CLI의 Device OAuth·계정 상태·live 모델·스트리밍 계획 생성만 TripPilot에 연결한다. TripPilot은 CLI credential을 소유하지 않으며, 로컬 MVP는 런타임 오류와 무관하게 유지돼야 한다.

### 구현 태스크

- [ ] 외부 `alpine-codex-cli-client` source를 정확한 commit으로 고정하고, build/asset 재현 방법을 문서화한다.
- [ ] `integration/codex-alpine`에 `CodexRuntimePort` 구현체를 만들고 UI·도메인 모듈로 runtime 타입이 누출되지 않게 한다.
- [ ] runtime 준비 상태, 오류 코드, 계정 연결 상태를 TripPilot의 제한된 상태 모델로 변환한다.
- [ ] 공식 CLI가 시작한 Device OAuth browser handoff와 앱 복귀 후 상태 재확인을 구현한다. OAuth redirect/token 교환은 TripPilot이 구현하지 않는다.
- [ ] 연결 해제는 CLI 측 logout/정리 동작을 호출하고 TripPilot의 표시 상태만 제거한다. credential 파일을 직접 삭제하거나 읽지 않는다.
- [ ] Codex CLI가 반환한 live 모델 목록만 보여주고, 여행 계획에 허용한 모델만 선택 가능하게 필터링한다. 모델 ID를 하드코딩하지 않는다.
- [ ] `TripPlanningRequest`와 `ReservationAnalysisRequest`를 고정된 instruction과 함께 runtime으로 보내고, 출력은 각 draft validator를 통과한 경우에만 Phase 3 검토 화면에 전달한다.
- [ ] runtime의 승인된 research 응답 capability가 확인된 경우에만 `WeatherAdvisoryRequest`를 연결한다. capability가 없거나 오류면 "현재 이 Codex runtime에서는 날씨 참고를 제공할 수 없음"을 표시하고, 다른 Provider·browser automation·자동 fallback을 실행하지 않는다.
- [ ] 스트리밍, 사용자의 Stop, OAuth 취소/만료, runtime unavailable, background/foreground, force-stop 복구 상태를 구현한다.
- [ ] raw command, raw argument, 임의 app-server method, Grok fallback, 자동 prompt replay를 모두 차단한다.
- [ ] CLI credential·token·계정 세부정보가 TripPilot DB, DataStore, analytics, crash log, export로 들어가지 않는지 코드·실행 경로를 감사한다.

### 자체 테스트

- [ ] mock/contract 테스트: 상태 변환, OAuth 시작 요청, 취소, logout, model list, stream, stop, 오류 mapping을 검증한다.
- [ ] 사용자가 직접 승인한 전용 테스트 계정으로 Device OAuth 성공·취소·앱 복귀·로그아웃·재로그인을 검증한다. 개인 자격 증명은 기록하지 않는다.

## Phase 5. 외부 실행·보안·출시 검증

### 목표

사용자가 검토한 여행 데이터를 Android 시스템 기능으로 안전하게 전달하고, 보안·개인정보·라이선스·배포 조건을 검증한다. 이 단계에서만 실제 제품 APK의 사용 가능 여부를 최종 판단한다.

### 구현 태스크

- [ ] 사용자가 명시적으로 선택한 일정만 Calendar Provider에 추가하도록 confirmation UI와 권한 흐름을 구현한다. `CalendarAction`은 `REVIEW_REQUIRED/APPROVED/EXECUTED/FAILED/REJECTED`만 가지며, 기존 이벤트 marker로 중복 추가를 막고 부분 실패 항목만 재시도한다. 다른 이벤트 수정·삭제와 TripPilot이 만든 이벤트의 자동 삭제는 구현하지 않는다.
- [ ] 지도 장소와 예약·출처 URL은 사용자 선택 후 Android Intent/Custom Tabs로만 연다. 출처 재확인은 browser 복귀 뒤 사용자가 `UNCHANGED/CHANGED/FAILED`를 기록하는 흐름으로 끝나며, WebView 로그인 자동화는 추가하지 않는다.
- [ ] Storage Access Framework로 선택 itinerary만 RFC 5545 `.ics`로 내보내고, Calendar 권한 없이 동작하게 한다.
- [ ] Storage Access Framework로 `trippilot.trip-backup` v1 JSON을 export/import한다. legacy `openminis.trip-backup` v1 reader도 검증한다. import는 schema/size/field limits를 검증하고 항상 새 Trip 사본을 만들며 OAuth/chat/browser/CalendarAction/reminder 상태는 넣지 않는다.
- [ ] readiness reminder Android delivery를 연결한다. 알림 권한을 사용자가 허용하고 설정을 켠 경우에만 D-7~D-1 미완료 알림을 하나 예약하며, boot 뒤 DB source of truth에서 다시 동기화한다.
- [ ] 외부 실행 직전에 대상, 시간, URL, 취소 동작을 보여주고, 실행 실패·권한 거부·사용자 취소를 처리한다.
- [ ] backup/D2D 제외, app-private 저장소, 민감 로그 차단, 화면 보안 적용 범위를 검토한다. `FLAG_SECURE`는 OAuth/AI 민감 화면에만 적용할지 사용성 영향과 함께 결정한다.
- [ ] `docs/privacy-and-egress.md`에 로컬 저장 데이터, Codex로 전송되는 데이터, OAuth 소유 주체, 외부 Intent 동작, 로그 정책을 확정한다.
- [ ] `docs/third-party-notices.md`에 TripPilot, Alpine Codex client, Codex CLI, Alpine, PRoot 및 번들 구성요소의 고지·소스 제공·재현성 검토 결과를 반영한다.
- [ ] release build variant, signing 입력 방식, runtime asset hash/lock 검증, ABI 정책, 버전 정책을 문서화한다. 실제 서명 키는 저장소에 넣지 않는다.
- [ ] `docs/test-matrix.md`에 에뮬레이터·arm64 실기기·offline·OAuth·permission·데이터 무결성·접근성·light/dark·font scale·screenshot 회귀 매트릭스를 작성한다.
- [ ] Compose Preview Screenshot Testing 또는 동등한 deterministic screenshot test로 핵심 네 화면의 golden을 승인하고 CI/local `verify`에 연결한다.
- [ ] 제품의 startup·여행 목록·상세 화면·AI 초안 검토 흐름을 포함하는 Baseline Profile 후보를 생성·측정한다. APK 직접 배포 채널에서의 적용 한계는 문서에 명시한다.

## 최종 결과 요약

완료 시 TripPilot은 OpenMinis와 독립된 Android 여행 관리 앱이며, 로그인 없이도 여행 생성·일정·Preparation/Packing·예약·출처 재확인·로컬 알림·백업/ICS를 제공한다. 사용자가 원할 때만 Codex CLI OAuth로 여행/예약/조건부 날씨 초안을 생성하며, 모든 데이터 반영과 Calendar·지도·브라우저·파일 실행은 사용자 검토·승인 뒤에 일어난다.

## 잔여 리스크 / 후속 과제

- Alpine/PRoot·Python·CLI 번들로 인한 APK 크기, 첫 준비 시간, `arm64-v8a` 제약은 실제 기기 지표로 재평가한다.
- Codex CLI/app-server의 변경은 고정 commit·버전·호환성 회귀 테스트로 관리한다.
- GPL 및 상위 구성요소 배포 의무는 실제 배포 전 법률·라이선스 검토가 필요하다.
- 멀티 Provider, 서버 동기화, 협업·공유, 자동 리서치/예약은 v1 완료 뒤 별도 개발 계획으로만 검토한다.
